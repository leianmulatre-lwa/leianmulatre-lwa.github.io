# Map transit · Phase 2 live-feed plan

Phase 1 (shipped 2026-11-18) is a visual guide built from data we already have:
coloured line badges, "toward" terminals from published stop order, a live bus/rail
key, and a compact line key in `#mapMetroLineKey`. It does **not** claim arrivals,
delays or disruptions.

Phase 2 adds real predictions and alerts. This document is the implementation plan;
no live-feed code or API key is added by the Phase 1 change.

## Verified source position

Metro's Open Data site states that GTFS-realtime is provided through **Swiftly** and
requires an API key requested through Swiftly's API Key Request Form. The documented
agency keys are `lametro` (bus) and `lametro-rail` (rail). Swiftly exposes both
protobuf and JSON GTFS-realtime, updates VehiclePositions about every 5 seconds and
TripUpdates about every 10 seconds, and Metro explicitly does not guarantee accuracy
or timeliness. Source: <https://developer.metro.net/api/> (checked 2026-11-18).

The existing map uses two public Metro WebSocket feeds for vehicle dots only:

- `wss://api.metro.net/ws/LACMTA/vehicle_positions`
- `wss://api.metro.net/ws/LACMTA_Rail/vehicle_positions`

Those feeds are useful for "where is a vehicle now" but do not provide a trustworthy
countdown, delay or service-alert panel by themselves.

## Architecture

1. **Keep the browser thin.** Add a same-origin Worker route, e.g.
   `/api/transit/live?agency=bus|rail`, instead of putting a Swiftly key in
   `map-app.html`. The Worker holds `SWIFTLY_API_KEY` as a secret, allowlists the two
   agency keys, and returns a small normalised JSON payload. No user location, account
   data or search history is sent upstream.
2. **Fetch only while opted in.** The existing `LA Metro live` button remains the
   gate. Starting live transit begins polling; stopping it, `pagehide`, or leaving the
   map ends polling. Poll TripUpdates no more often than every 30 seconds in the
   browser (well under Swiftly's update cadence) and cache Worker responses for 15–30
   seconds.
3. **Join against static data.** Use `data/metro-rail-map.json` for line colour, line
   name and terminal direction. For bus, use a served static GTFS snapshot (routes,
   stops, trips, stop times, headsigns) generated from Metro's published GTFS. Match
   `trip_id`, `route_id` and `stop_id`; never guess a stop from a dot alone.
4. **Normalise the payload.** The Worker should emit only what the UI needs:
   `routeId`, `routeName`, `color`, `directionId`, `headsign`, `stopId`, `stopName`,
   `predictedArrival` (ISO time), `delaySeconds`, `vehicleId`, `sourceUpdatedAt`, and
   `alerts[]` with a short headline/URL. Drop anything older than a defined freshness
   window and expose `feedStatus: live | stale | unavailable`.
5. **Show provenance and uncertainty.** Every prediction panel must read
   "LA Metro · Swiftly GTFS-realtime" and carry a Metro-style accuracy caveat. Times
   are shown as "about 4 min" with the clock time on hover, never as a guaranteed
   arrival. If a feed is stale, say so instead of displaying a frozen countdown.

## UI rollout

- Extend `.transit-line-detail` from Phase 1: after the line badge and toward
  terminal, add the next three named stops with predicted minutes and a last-updated
  line. Keep the existing "GPS positions do not identify a driving lane" caveat.
- Add a small alerts strip above the live key only when `alerts[]` is non-empty. Link
  to Metro's official service-status page for details. No unverified incident text is
  generated by BIG LWA.
- Use the same coloured badge in live dots, the line key and itinerary steps so a
  rider can match "the purple 802" across the map, key and directions.
- Keep Apple Maps as the final transit-directions handoff until BIG LWA has a tested
  multimodal itinerary engine. The handoff remains an explicit user action.

## Required before launch

- Swiftly API key approval and a Worker secret; confirm permitted domains/terms.
- Decide whether Metro's GTFS-RT Alerts entity is included. If not, show alerts from
  Metro's official service-status page as a link, not as invented feed data.
- Generate and version a static bus GTFS snapshot, with source URL and checked date,
  following the existing `data/metro-rail-map.json` pattern.
- Add regression tests for: opt-in only, no key in client source, 30-second poll floor,
  stale-feed messaging, stop/route matching, alert provenance, and no automatic GPS.
- Run the full map regression suite plus a live-browser check in both the standalone
  map and the Studio iframe before bumping the shared map asset version.

## Explicit non-goals for this phase

No live Uber/Lyft/Waymo quotes, no provider scraping, no automatic location access,
no third-party checkouts inside the map, and no claim that vehicle dots equal arrival
predictions or driving lanes.
